Trajectory Inference & Fate Mapping — Design, Method & Sources

Scoped toward one specific question: tracking differentiation from bone-marrow progenitors through to mature immune cells infiltrating the tumor microenvironment (TME), in pooled Evercode samples spanning both compartments. Covers the experimental design this analysis actually needs, the method (PAGA + CytoTRACE + CellRank, no RNA velocity), and the pipeline steps that implement it.

Read this first

Unlike the other docs/*_deep_dive.html reports in this repo, this document does not contain results from a real run — no bone-marrow+TME dataset exists yet to run it against. It documents the method, the code (scripts/08_trajectory_paga.py, scripts/09_cellrank_fate_mapping.py), and what the experiment needs to look like for the analysis to produce a meaningful answer. Treat every number in the "experimental design" section as general, adaptable guidance, not a fixed requirement — refine it once your actual cohort is defined.

Motivation

Why this needs trajectory tools, not just clustering

The core pipeline (QC → normalize → cluster → annotate) answers "what cell types are present." It doesn't answer "which cells are becoming which other cells, and how far along that process are they." Tracking bone-marrow-derived progenitors as they differentiate into mature immune cells infiltrating a tumor is fundamentally a question about ordering and direction — exactly what clustering discards and trajectory/fate-mapping methods are built to recover.

There's real precedent for this specific biological question: a pan-cancer single-cell atlas of tumor-infiltrating myeloid cells modeled monocyte-to-tumor-associated-macrophage differentiation trajectories across multiple cancer types and found consistent, reproducible transcriptional trajectories despite substantial inter-patient and inter-cancer-type heterogeneity5 — useful prior art for both what the trajectory should look like biologically and how much patient variability to expect.

Experimental design

What the data needs to look like for this to work

Paired compartments, not just more cells

No trajectory or fate-mapping method invents biological anchors that aren't in the data. To recover a bone-marrow-to-TME trajectory, the pooled Evercode run needs cells sampled from both ends of the process, ideally from the same subjects:

  • Bone marrow (aspirate/biopsy) — the progenitor/HSPC-containing compartment, needed as the trajectory's root.
  • Tumor tissue (or TME-proximal tissue) — the terminal/mature-state compartment.
  • Peripheral blood, if feasible, is a valuable intermediate — many myeloid trajectories transit through a circulating monocyte state between bone marrow and tissue infiltration, and having that intermediate sampled directly (rather than only inferred) makes the trajectory much easier to validate.

Whichever compartments are included, each cell's tissue-of-origin needs to survive as a real metadata column all the way through the pipeline — scripts/00_load_parse_output.py already preserves whatever columns exist in cell_metadata.csv (this is how the existing sample/donor column survives), so a compartment (or similarly named) column with values like bone_marrow / blood / tumor will carry through automatically as long as it's present in the Evercode metadata from the start. This has to be planned into the sub-library/well design before sequencing, not recovered afterward.

How many subjects/replicates

There's no single correct number — it depends on effect size and the inter-patient heterogeneity in the specific cancer type, which this pipeline can't estimate in advance. As general orientation, not a requirement:

  • Single-lab scRNA-seq studies comparing groups/conditions commonly use somewhere in the range of 3–6 biological replicates per group as a practical minimum for a first pass — enough to see whether a pattern is consistent across individuals rather than being one person's idiosyncrasy, without requiring cohort-study-scale recruitment.
  • Trajectory-specific work benefits from more than that where possible, because the most informative cells — those actually mid-transition — are typically the rarest population in the data. A design that's adequately powered for cluster-level comparisons can still under-sample the transitional states that make a trajectory result credible.
  • The reference pan-cancer myeloid study above pooled data across a much larger number of patients and multiple cancer types (a meta-analysis-scale atlas, not a single-lab experiment) — useful for showing what a well-powered version of this question looks like, not a target to match for a first pooled Evercode run.

Practical recommendation: treat the first pooled run as a pilot. Confirm the trajectory looks biologically sane (root cluster genuinely progenitor-like, terminal states genuinely mature/TME-associated, fate probabilities vary smoothly rather than looking like noise) before committing to a larger cohort sized around a specific effect you're trying to detect.

Integration strategy needs to change for this specific analysis

Don't Harmony-integrate away the signal you're studying

scripts/02b_harmony_integration.py defaults to --batch-key sample (donor), which is the right call for the core pipeline's QC→cluster→annotate path. For trajectory analysis across bone-marrow and tumor compartments specifically, do not also integrate across compartment the same way — that would actively erase the biological signal this whole analysis exists to find. Keep Harmony scoped to donor-level batch correction only; let compartment-driven differences remain in the embedding, since that's the trajectory.

Method

PAGA, CytoTRACE, and CellRank — what each one actually computes

PAGA — coarse connectivity graph

PAGA1 builds a graph where each node is a cluster/cell-type and each edge weight reflects how well-connected two populations are in the underlying neighbor graph. It's a summary of which transitions are plausible given the data's structure — not a directed trajectory by itself, and not proof that a transition actually happens. Cheap to compute directly on the existing Harmony-corrected, clustered, annotated object; no new data required.

CytoTRACE — differentiation potential from transcriptional diversity

CytoTRACE2's core finding: the number of distinct genes expressed per cell correlates with how undifferentiated that cell is — stem/progenitor cells tend to express a broader, more diverse gene repertoire than terminally differentiated cells. This gives a per-cell "developmental potential" score without needing spliced/unspliced counts, real time-course sampling, or lineage tracing. CellRank 2 reimplements this algorithm directly in Python (cellrank.kernels.CytoTRACEKernel) — no separate R package, no extra dependency beyond CellRank itself.

CellRank 2 — kernels, GPCCA, and fate probabilities

CellRank 23 (code: github.com/theislab/cellrank; what's new vs. v1: cellrank.readthedocs.io/en/latest/about/version2.html) separates trajectory inference into two independent pieces:

  • Kernels compute a cell-cell transition matrix from some data modality. CellRank 2 supports six: VelocityKernel, ConnectivityKernel, PseudotimeKernel, CytoTRACEKernel, RealTimeKernel, and PrecomputedKernel. This pipeline uses CytoTRACEKernel (directs the graph by differentiation potential) combined with ConnectivityKernel (stabilizes it against noise) and, optionally, PseudotimeKernel fed by scripts/08_trajectory_paga.py's diffusion pseudotime — combined via CellRank's documented weighted-sum kernel arithmetic (e.g. 0.7 * ctk + 0.3 * ck).
  • Estimators analyze the transition matrix. GPCCA (Generalized Perron Cluster Cluster Analysis) is CellRank's recommended estimator: it computes coarse-grained "macrostates," automatically classifies some as initial and terminal states, and computes each cell's fate probability — the likelihood of eventually reaching each terminal state — plus lineage driver genes, the genes most correlated with progress toward a given fate.

Verified against CellRank's own current API documentation and tutorial notebooks before writing any code (not from memory alone) — the real, current workflow is compute_schur() → compute_macrostates(n_states, cluster_key) → predict_terminal_states() / predict_initial_states() → compute_fate_probabilities() → compute_lineage_drivers(). (CellRank's older .fit() convenience method still appears in some quick-start examples but is marked deprecated in the current API reference — this pipeline uses the granular, current calls.)

Pipeline steps

scripts/08_trajectory_paga.py + 09_cellrank_fate_mapping.py

Both are optional steps after the core pipeline (QC → normalize → Harmony → cluster → 04b annotation). Neither requires new raw data.

08 — PAGA + diffusion pseudotime

python scripts/08_trajectory_paga.py --input 04b_annotated.h5ad --output 08_paga.h5ad \
    --plot-dir paga_plots/ --annotation-col cell_type_v2 --root-cluster HSPC

--root-cluster is required and consequential: diffusion pseudotime measures distance from this population, so it sets the direction of every downstream result. Point it at whichever 04b_better_annotation.py label is the genuine progenitor population (its 12-category dictionary already includes an HSPC category for exactly this). The specific root cell within that cluster is auto-selected by a documented heuristic (most extreme value along the first diffusion component) — override with --root-cell-index if a better candidate is known.

09 — CellRank fate mapping

python scripts/09_cellrank_fate_mapping.py --input 08_paga.h5ad --output 09_cellrank.h5ad \
    --plot-dir cellrank_plots/ --drivers-csv lineage_drivers.csv \
    --annotation-col cell_type_v2 --n-states 8 --use-dpt-pseudotime

--n-states should comfortably exceed the number of distinct initial+terminal populations you actually expect — GPCCA needs headroom to find the real structure; too few states forces distinct biology to collapse together. Inspect cellrank_plots/eigenvalue_spectrum.png (a real eigenvalue gap indicates a natural number of states) rather than trusting the default blindly.

Outputs: fate-probability UMAPs, a circular projection of fate probabilities per cell type, the coarse-grained macrostate transition matrix, and a CSV of lineage driver genes per terminal state — plus the fitted GPCCA estimator itself (*.gpcca.pickle, via CellRank's own write()/read() serialization) so later plotting or reporting doesn't require recomputing the Schur decomposition and macrostates from scratch.

HPC

pipeline/run_trajectory.slurm chains both steps, run after run_pipeline.slurm/run_downstream.slurm have already produced an annotated object:

sbatch --account=<your-account> --qos=<your-qos> \
  --output=/path/to/logs/scrna-trajectory-%j.out \
  pipeline/run_trajectory.slurm /path/to/OUT_DIR cell_type_v2 HSPC 8

Scope decision

Why not RNA velocity (yet)

True RNA velocity4 compares spliced vs. unspliced transcript ratios to predict the near-term direction of each cell's expression change — a genuinely different, more direct signal than CytoTRACE's static differentiation-potential heuristic. It's not included here for a concrete reason: standard Parse split-pipe/Trailmaker gene-count output does not separate spliced from unspliced reads. Getting real velocity would mean reprocessing raw FASTQs through a velocity-aware aligner (e.g. STARsolo's Velocyto mode) — a raw-data pipeline change, not a downstream script addition, and not yet confirmed whether the current split-pipe version even supports producing velocity-compatible output. That needs checking against Parse's current documentation before it's worth committing to.

CytoTRACE + PAGA + CellRank gets real directional/fate information now, from data this pipeline already produces, while that question stays open. If real velocity is added later, cellrank.kernels.VelocityKernel slots into the same CellRank/GPCCA workflow already built here — the estimator and downstream analysis code wouldn't need to change, only the kernel.

Caveats

What this analysis can and can't claim

  • Inference from a single snapshot, not lineage tracing. Nothing here follows an actual cell over time. Fate probabilities are statistical inferences from the geometry of a single time-point's transcriptomes — treat them as hypotheses about likely trajectories, not observed lineages.
  • CytoTRACE and pseudotime both assume a roughly monotonic differentiation process. Immune cell states aren't always unidirectional — macrophage polarization and some myeloid states show real plasticity that a pseudotime-style ordering can misrepresent as strictly one-way.
  • The root-cluster choice is a modeling decision, not a measurement. Every downstream diffusion-pseudotime and CytoTRACE-direction result is conditioned on which population was designated the root and, within it, which single cell was auto-selected — a heuristic, documented as such in scripts/08_trajectory_paga.py, not a certainty.
  • The number of macrostates (--n-states) is a hyperparameter requiring inspection, not a ground truth — check the eigenvalue spectrum plot before trusting a specific terminal-state count.
  • The compartment-crossing claim only means something with real paired compartment data — see Experimental design. Run against single-compartment data and the "trajectory" is really just describing within-compartment heterogeneity, not bone-marrow-to-TME differentiation.
