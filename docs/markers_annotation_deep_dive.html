Marker Detection & Annotation — Method, Validation & Comparison

A detailed look at scripts/04_markers_annotation.py: Wilcoxon marker detection compared against a t-test, and a marker-based annotation experiment that honestly shows how much annotation quality depends on marker specificity, not just marker presence.

Script: scripts/04_markers_annotation.py Validated against: public PBMC3k (10x Genomics) Status: local, not yet run on Parse data

01 · Method

What the script actually computes

Input is the clustered .h5ad from the clustering step. Two operations:

  1. Marker detection: sc.tl.rank_genes_groups(method="wilcoxon") — a nonparametric rank-sum test, one cluster vs. the rest, for every cluster at the chosen resolution. This is scanpy's equivalent of Seurat's default FindMarkers test.
  2. Annotation (demo): a small canonical-marker dictionary is scored per cell (sc.tl.score_genes), averaged per cluster, and each cluster gets the label with the highest mean score. This dictionary is PBMC-specific and explicitly not meant to generalize to other tissue.

03 · Wilcoxon vs. t-test

How much does the statistical test change the marker list?

Re-ran marker detection on the identical clusters with method="t-test" instead of "wilcoxon", and compared the top-10 genes per cluster:

Average overlap: 7.7/10. The two tests agree on the dominant identity-defining genes in every cluster (the top 1–2 genes are essentially always shared); they diverge more on secondary genes, most visibly in cluster 5 where the two nearby myeloid populations (monocyte and dendritic cell) share enough biology that the exact gene ranking is more sensitive to which test is used.

Practical takeaway

Wilcoxon (the default here, and Seurat's default too) is more conservative about assumptions than the t-test — it doesn't assume the expression values are normally distributed, which single-cell count data generally aren't. The overlap is high enough that either test would support the same biological conclusions in this dataset, but Wilcoxon is the more defensible default.

04 · Annotation: broad vs. tight markers

A real failure mode, then a real fix

The QC and prior deep-dive reports each showed methods agreeing closely. This section shows the opposite: an experiment that broke, and why.

Attempt 1: adding a "Dendritic cell" category with broad markers

Cluster 5's top genes (FCER1A, CST3, HLA-DPB1, HLA-DPA1) are a textbook dendritic-cell signature, but the demo script's marker dictionary doesn't include a DC category at all — so cluster 5 gets absorbed into "Monocyte" (still the best-scoring available label, just not the right one). Adding DC with those same four genes as its marker set seemed like the obvious fix:

ClusterLabel with broad DC markers (FCER1A, CST3, HLA-DPB1, HLA-DPA1)
0T cell — correct
1B cell — correct
2Dendritic cell — wrong, this is CD14+ monocyte
3NK cell — correct
4Dendritic cell — wrong, this is FCGR3A+ monocyte
5Dendritic cell — correct

What went wrong

CST3, HLA-DPB1, and HLA-DPA1 aren't DC-exclusive — they're broadly expressed across antigen-presenting myeloid cells, monocytes included. The DC score ended up inflated across every myeloid-like cluster, not just the real DC population, and stole two monocyte clusters that were correctly labeled before DC even existed as a category.

Attempt 2: tightening the marker set

Dropped the shared MHC-II/CST3 genes and kept only FCER1A and CLEC10A for the DC category (more specific to conventional DCs in blood), and strengthened the monocyte set with S100A8/S100A9:

ClusterLabel with tight DC markers (FCER1A, CLEC10A)
0T cell — correct
1B cell — correct
2Monocyte — correct
3NK cell — correct
4Monocyte — correct
5Dendritic cell — correct

Key result

Marker-score annotation is only as good as marker specificity, not marker relevance — genes that are real markers of a cell type but also expressed elsewhere can actively make annotation worse, not just uninformative, by contaminating adjacent populations' scores. This is the concrete version of the caveat the main pipeline doc already raises about reference-based/foundation-model annotation being sensitive to how well the reference actually covers and distinguishes the real cell-type space.

05 · Caveats

What this does not establish

Not yet validated on real project data

Every marker dictionary here is PBMC-specific. Real Parse Evercode data (whatever tissue it turns out to be) will need its own tissue-appropriate marker set built the same careful way — broad-then-tightened, checked against the actual top marker genes rather than assumed from literature alone.

This is not reference-based annotation

The scoring approach here is a lightweight demo, not the more robust reference-based methods (label transfer, scANVI/scArches) the main pipeline doc lists as available options. The specificity lesson above applies to those methods too, but they have more machinery for handling it than a simple argmax over hand-picked gene sets.
